# ClickHunter — audit et corrections du 31 octobre 2026

## Périmètre et méthode

Base examinée : commit `9c3db42`. Cible : Paper 1.21.4, Java 21, SQLite WAL. Le texte fourni demande une revue transversale avec corrections ; sa section 17 ne contient aucune idée renseignée. Aucune nouvelle mécanique majeure ni modification de prix, gains, monnaies ou progression n’est ajoutée par cet audit.

L’[inventaire reproductible](INVENTAIRE-AUDIT.md) indexe les **195 fichiers Java de production et 38 fichiers YAML**. La revue s’appuie sur l’inventaire de tous les composants, les recherches transversales (événements, tâches, SQL, accès asynchrones, erreurs et commandes), l’examen ciblé des parcours sensibles et les tests. Cet index exhaustif n’est pas une preuve que chaque ligne et chaque combinaison de configuration est exempte de bug.

| Ensemble examiné | Points contrôlés et preuves |
| --- | --- |
| Noyau, runtime, dépendances | Activation/arrêt, ordre des services, annulation des tâches, Java 21/Paper 1.21.4, dépendances optionnelles et réflexion. |
| Économie, AH, enchères, livraisons | Transactions SQL existantes, frais entiers, clés idempotentes, contrôles de solde et dépassements, sortie/réception d’objets ; tests de concurrence et de récupération de la suite existante. |
| Combat, boss, raids, piñata, PNJ | Sessions, invitations, sorties refusées, état d’observation, permissions de retour, apparition des créatures, tâches de maintenance et chargement des skins. |
| Progression, équipements, ressources | Données d’upgrade/prestige, sacs et snapshots, calendrier daily, compression 64→1 ; suite de régression existante et limites de crash décrites plus bas. |
| Navigation, avant-postes, BuyZone | Isolation des inventaires, droits de zones, accès aux instances et dépendance LuckPerms absente. |
| UI, social, affichage | Désactivation des boutons, vues tardives, tchat asynchrone, caches concurrents déjà présents, coût du scoreboard, documentation des commandes et conservation des personnalisations. |

## 1. Défauts identifiés et corrections

Aucune nouvelle faille P0 de duplication reproductible n’a été démontrée pendant cette passe. Cela ne certifie pas les échanges entre playerdata et SQLite contre toutes les coupures possibles.

| Priorité | Défaut réel et origine | Correction et vérification |
| --- | --- | --- |
| P1 | Sans LuckPerms, Paper refusait l’enregistrement des événements BuyZone : des méthodes synthétiques de lambda exposaient `UserManager`, `User` et `CachedPermissionData`, pourtant optionnels. Le module annonçait ensuite être actif. | Accès aux permissions hors ligne isolé dans `integration/LuckPermsAccess`. Test par chargeur de classes qui interdit LuckPerms ; validation Paper sans ce plugin. Aucun ajout de dépendance obligatoire. |
| P1 | La création d’un skin PNJ appelait `createStaticDescriptor(name)` sur le thread serveur. Le JAR ZNPCsPlus 2.0.0 fait un `CompletableFuture.join()` réseau dans cette méthode ; pause locale observée de plus de quatre secondes. | Utilisation de `createRefreshingDescriptor`, dont la récupération est différée par ZNPCsPlus. Test du choix de fabrique non bloquante ; PNJ et pseudos sauvegardés conservés. Le rendu final du skin dépend toujours du fournisseur et de ses accès réseau. |
| P1 | Une sortie refusée retirait le joueur du groupe de raid malgré sa présence dans l’arène. | Vérification de la destination effective avant retrait du groupe ; message invitant à réessayer. Test de téléportation annulée puis autorisée. |
| P1 | Une sortie refusée supprimait le statut d’observation et la position de retour avant la téléportation ; le joueur resté sur place pouvait redevenir une cible. | Conservation de l’état et du retour jusqu’au succès ; suppression après téléportation effective. Test avec observateur, sortie annulée puis retour à la position d’origine. |
| P1 conditionnel | Une téléportation fournie par un autre plugin pouvait franchir le portail d’un seul saut et atterrir juste au-delà : seul le point d’arrivée dans la boîte était contrôlé. | Vérification supplémentaire de l’intersection du segment de téléportation vers le côté verrouillé. Retour vers le nord autorisé. Test échouant avant correction puis passant après ; les droits créatif/staff sont conservés. |
| P1 | `/raid rejoindre` ne revérifiait pas le droit de zone après le lancement. | Zone du parchemin conservée dans le groupe ; vérification des droits, de la mort et de l’isolation avant le retour. Test de permission retirée puis réaccordée. |
| P1 | Une exception dans un arrêt de module interrompait les arrêts suivants, y compris la fermeture de SQLite. | Chaque étape d’arrêt est protégée séparément ; l’erreur complète est journalisée en SEVERE et les étapes suivantes sont exécutées dans le même ordre. Test d’échec simulé suivi d’une étape de fermeture. Ce test ne simule pas une panne physique du disque. |
| P2 | Une entrée de raid annulée conservait une fausse position de retour. | Enregistrement du retour seulement après entrée réussie ; test dédié. |
| P2 | Remplacer un bouton actif par une icône sans action ne retirait pas son ancien callback. | `Menus.View.put(..., null)` supprime aussi l’action précédente. Test de clic sur une barrière remplaçant un achat. Aucun achat gratuit n’a été démontré : les validations économiques existantes restent nécessaires. |
| P2 | Deux tâches du gestionnaire de mobs n’étaient pas annulées explicitement ; un second démarrage pouvait ajouter des boucles. Le gestionnaire de classements holographiques n’avait pas d’arrêt propre. | Références conservées, démarrages idempotents, annulation à l’arrêt, garde sur les callbacks tardifs. Le noyau arrête le gestionnaire de classements avant le fournisseur partagé. Tests sur les véritables handles du scheduler MockBukkit. |
| P2 | Une évacuation différée à la connexion pouvait téléporter un joueur ayant déjà quitté son ancienne instance. | Vérification de la session actuelle, du monde actuel, de l’appartenance au groupe et du droit staff au moment du callback. |
| P2 | Le scoreboard ouvrait une connexion et une requête par joueur à chaque cycle. | Lecture groupée, connexion unique et transaction de lecture ; lots de 500 paramètres maximum. Les vues et connexions périmées sont écartées avant affichage. Tests des valeurs, d’un lot de 600 joueurs, des doublons et d’un compte absent. |
| P2 | La migration visuelle pouvait remplacer une ligne personnalisée contenant plusieurs statistiques par une seule statistique. | Conservation des lignes combinées ; test d’une ligne Écus + Gemmes. |
| P3 | La documentation Daily décrivait encore une migration vers 28 jours et une lootbox au jour 1. Un ancien tableau d’audit affirmait à tort que l’ATM n’avait pas de transaction. | Documentation alignée sur les 31 jours et les petits montants actuels ; distinction entre journal interne de livraison et courrier entre joueurs. |

Les quatre premiers scénarios unitaires de cette passe ont été exécutés avant correction : **quatre échecs reproduits** (bouton remplacé, groupe quitté malgré refus, état d’observation perdu, faux retour d’entrée). Les mêmes scénarios passent après correction. Le défaut LuckPerms et la pause de skin ont été détectés ensuite sur Paper. Un cinquième test de reproduction a confirmé le saut de téléportation au-delà du portail avant sa correction.

## 3. Performances et données

Pour 1 à 500 joueurs concernés par un cycle de scoreboard, une seule requête lit les soldes et éliminations au lieu d’une par joueur. Au-delà, les requêtes sont découpées en lots de 500 dans la même connexion et transaction de lecture. Un joueur absent de la base reçoit un instantané vide sans création de compte ni attribution de monnaie. Le SQL reste sur l’exécuteur existant ; les joueurs, sessions et scoreboards ne sont manipulés que sur le thread serveur.

Mesure reproductible : `BatchSnapshotsTest`, trois cycles de 100 joueurs, base SQLite locale, mêmes valeurs vérifiées. Une première exécution a mesuré **271,4 ms en lectures individuelles contre 5,7 ms groupées**. Une exécution finale a donné 190,3 ms contre 3,7 ms. Le test ne fixe aucun seuil temporel dépendant de la machine. Ce résultat ne mesure ni les TPS de production, ni le coût des paquets graphiques, ni un serveur de 100 joueurs réels.

L’attente réseau synchrone des skins est supprimée du chemin de création/restauration. Aucun nouveau pool ni mécanisme d’affinité CPU n’est ajouté : les opérations Bukkit continuent de respecter le thread principal de Paper. Les tâches arrêtées ne doivent plus relancer de créations d’entités ou de textes depuis un résultat ancien.

## 4. Sécurité et limites

Les contrôles de solde, débits, frais, droits et écritures idempotentes restent côté serveur. La nouvelle lecture groupée ne comporte aucune écriture. Les noms de colonnes dynamiques examinés viennent des enums internes ; les UUID et valeurs utilisateur passent par les paramètres SQL.

Les observateurs restent protégés lorsque la sortie est annulée. Le retrait d’un accès de zone est appliqué aussi à une tentative de retour en raid. Une permission administrateur ne transforme pas automatiquement un visiteur staff en membre du groupe.

Limites maintenues explicitement :

- La date du Daily et les commandes console arbitraires ne font pas partie d’une même transaction. Une coupure entre validation et exécution demande encore une vérification administrative. Rejouer toutes les commandes automatiquement pourrait doubler des récompenses externes ; aucune relance aveugle n’a été ajoutée.
- Les transferts entre inventaires Bukkit et SQLite doivent continuer à être testés par injection de pannes à chaque étape. Le journal `/claim`, les reçus de sortie et les snapshots de sacs existants sont conservés ; cette passe ne certifie pas toutes les fenêtres de coupure des transformations/compressions.
- Aucun test de panne matérielle, de corruption réelle de fichiers ou de saturation avec une communauté connectée n’a été exécuté. Les groupes privés sont en mémoire et les combats en cours ne sont pas repris à l’identique après un redémarrage ; ce contrôle de persistance porte sur les portails et les PNJ, pas sur la reprise d’un combat.
- L’environnement local a reçu des erreurs HTTP 504 de Mojang et 429 du serveur de secours pour le skin `Nati144378`. La récupération différée évite le blocage du serveur, mais le skin exact n’est donc pas certifié par cet essai.
- Le fournisseur Holographic Displays compatible 1.21.4 et ItemsAdder ne sont pas présents dans le serveur isolé utilisé ici : secours natif et icônes vanilla seulement. La perception visuelle du skin, des couleurs et de la musique demande un client graphique.

## 5. UI/UX et documentation

Les boutons sans action sont effectivement inactifs. Les messages de retour de raid expliquent le blocage et la marche à suivre. Les anciennes vues de scoreboard et les anciennes sessions ne sont pas actualisées par une réponse SQL tardive. Les personnalisations combinant plusieurs informations sont préservées.

Les couleurs et symboles de la mise à jour précédente sont conservés, de même que les notifications moins fréquentes. Pas de nouveau spam de tchat. Les 73 commandes déclarées dans `plugin.yml` possèdent une entrée dans le README ; leurs sous-commandes de raid restent documentées par catégorie. Cette passe ne crée aucune commande et ne renomme aucune permission.

- **414 tests automatisés : zéro échec, zéro erreur, zéro test ignoré.** Cela comprend les transactions/récupérations historiques, les nouveaux cas de cycle de vie, le chargement sans LuckPerms et le descripteur de skin différé.
- Lecture de plus de 500 UUID, résultat immuable, suppression des doublons et absence de création de solde vérifiées.
- Inventaire régénéré et correspondance des 73 commandes racines avec le README contrôlée.

Le portail sans LuckPerms a ensuite ouvert son offre lors de la téléportation au-delà du portail. **11 vérifications de parcours réussies**, puis **3 vérifications après arrêt propre et redémarrage** : portail restauré, PNJ Daily et PNJ d’accès au boss conservés avec doublons refusés. - L’arène de test utilise une difficulté Vache, un seuil d’un kill, des PV réduits et des dégâts nuls pour isoler les transitions. Cet essai ne valide pas l’équilibrage réel ni les dégâts des hautes zones. Les mondes et bases utilisés sont des copies de test ; aucune donnée de production n’est utilisée.

### Reproduire le scénario Paper

Le script `scripts/audit-paper-client.cjs` ouvre deux clients locaux sur `127.0.0.1:25581`. Il nécessite Mineflayer 4.39, un serveur Paper 1.21.4 **jetable**, le JAR compilé et ZNPCsPlus 2.0.0. Le joueur hors ligne `AuditSenior` doit être OP sur cette copie ; `AuditMember` doit rester joueur normal. LuckPerms doit être absent pour reproduire le cas de dépendance optionnelle.

**Ce scénario modifie les paramètres de combat, crée des PNJ et un portail, et pose un sol de test : ne jamais le lancer sur la production.** Une variable explicite est requise pour éviter un lancement accidentel :

```sh
CLICKHUNTER_DISPOSABLE_TEST=1 MINEFLAYER_MODULE=/chemin/vers/node_modules/mineflayer node scripts/audit-paper-client.cjs
```

Le script produit `audit-paper-results.json` (chemin personnalisable par `CLICKHUNTER_AUDIT_RESULTS`). Il ne charge pas de pack graphique ; les images, sons perçus et textures ItemsAdder restent hors de ses assertions.
